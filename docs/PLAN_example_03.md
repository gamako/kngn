# 実装計画 - Example 03: Sprite Rendering

> **配置更新（TASK-111.2）**: `src/sprite.zig` / `src/keyboard.zig` は `libs/gfx/src/` へ移設済み。本資料の `src/` パス記述は歴史的記録。

## 概要

**目的**: スプライトシステムの確立とPNG画像表示のデモンストレーション

このサンプルは、フェーズ2（ヘルパー関数群）の一環として、PNG decoderを統合し、再利用可能なスプライト描画モジュールを提供します。

## スプライトシステムの設計

### 責務

**`src/sprite.zig`の役割**:
- PNG画像からスプライトを作成
- フレームバッファへの描画（クリッピング処理込み）
- スプライトの状態保持と基本操作

**責務の境界**:
- ✅ 描画処理（ピクセルコピー、クリッピング）
- ✅ メモリ管理（PNG画像データの保持・解放）
- ✅ 状態の保持（座標x, y）
- ✅ 基本操作（move()メソッド - 座標の更新）
- ❌ イベント処理（呼び出し側の責任）
- ❌ ゲームロジック（いつどこに移動するか、衝突判定など - 呼び出し側の責任）

**設計方針**: Spriteは「データ構造 + 基本操作」を提供するヘルパー。アプリケーション側がイベント処理とゲームロジックを担当し、Spriteのmove()を呼び出す形で責務を分離。

### データ構造

**Sprite構造体**:
- PNG画像データ（PNGImage）
- 画面座標（x: i32, y: i32）

**API**:
- `init(allocator, path, x, y)` - PNG読み込みと初期位置設定
- `deinit(allocator)` - メモリ解放
- `move(dx, dy)` - 相対移動（x += dx, y += dy）
- `drawSprite(framebuffer, width, height, sprite)` - 描画（クリッピング処理込み）

## サンプル03の仕様

### 動作概要

- **ウィンドウサイズ**: 800x600
- **背景**: 黒（`@memset`でクリア）
- **スプライト**: `examples/image/usako.png`
- **初期位置**: 画面中央

### インタラクション

| 操作 | 動作 |
|------|------|
| 矢印キー | スプライトを移動（5px/フレーム） |
| ESC | 終了 |

### 処理フロー

1. **初期化**: プラットフォーム初期化 → スプライト読み込み
2. **メインループ**:
   - イベントポーリング
   - キー入力でスプライト座標更新
   - 背景クリア
   - スプライト描画
   - フレーム提示（60FPS制御）
3. **終了**: スプライト解放 → プラットフォーム終了

## ビルドシステムの統合

### 依存関係

**`src/sprite.zig`**:
- `png-decoder` モジュール（画像読み込み）

**`examples/03_sprite_rendering/main.zig`**:
- `sprite` モジュール（スプライト描画）
- `keyboard` モジュール（キー定義）
- `platform.h`（プリミティブAPI）

### ビルド方式

1. **ルートからの実行**: `zig build run-example_03`
   - 3つのプラットフォーム版を自動ビルド（objc/swift/metal）
   - ルートのbuild.zigでモジュール依存関係を一括管理

2. **独立ビルド**: `cd examples/03_sprite_rendering && zig build run`
   - サンプル単体でビルド・実行可能
   - 必要なモジュールを明示的に設定：
     ```zig
     // png-decoderモジュール
     const png_decoder_module = b.createModule(.{
         .root_source_file = .{ .cwd_relative = "../../libs/png-decoder/src/lib.zig" },
     });

     // spriteモジュール（png-decoderに依存）
     const sprite_module = b.createModule(.{
         .root_source_file = .{ .cwd_relative = "../../src/sprite.zig" },
     });
     sprite_module.addImport("png-decoder", png_decoder_module);

     // keyboardモジュール
     const keyboard_module = b.createModule(.{
         .root_source_file = .{ .cwd_relative = "../../src/keyboard.zig" },
     });

     // 実行ファイルにモジュールを追加
     exe.root_module.addImport("sprite", sprite_module);
     exe.root_module.addImport("keyboard", keyboard_module);
     ```

## クリッピング処理の設計

### 必要性

**問題**: スプライトが画面外にはみ出すとバッファオーバーランが発生

**解決**: 描画範囲を画面内に制限する

### 処理の概要

1. **早期リターン**: スプライトが完全に画面外なら描画しない
2. **範囲計算**:
   - ソース画像の描画開始位置（負の座標を考慮）
   - フレームバッファの書き込み位置
   - 実際に描画する幅・高さ
3. **ピクセルコピー**: クリップされた範囲のみ処理

### パフォーマンス考慮

- 画面外チェックによる早期リターン
- 必要最小限のピクセルのみコピー

---

## アルファブレンディングの扱い

### Phase 1での判断: 実装しない

**理由**:
- 実装複雑度が高い（RGB各チャンネルの計算）
- パフォーマンス影響が大きい（3〜5倍のコスト）
- 基本機能の検証に不要

**Phase 1の動作**:
- 単純コピー: `framebuffer[dst] = sprite[src]`
- 透明部分も上書き（不透明として扱う）

**Phase 2以降の検討事項**:
- アルファブレンディング関数の追加
- `drawSprite()` と `drawSpriteWithAlpha()` の分離
- パフォーマンスとの兼ね合い

## 設計判断の記録

### 判断1: sprite.zigの配置場所

**選択肢**:
- A) `libs/sprite-system/` - 独立ライブラリ
- B) `src/sprite.zig` - プロジェクト共通モジュール
- C) `examples/03_sprite_rendering/sprite.zig` - サンプル内

**決定**: B) `src/sprite.zig`

**理由**:
- `keyboard.zig`と同じ位置づけ（ヘルパーモジュール）
- 他のサンプルでも使える
- libsはより独立性の高いプロジェクト向け

### 判断2: 画像ファイルの選択

**決定**: `examples/image/usako.png` (既存)

**理由**:
- 既に用意されている
- 新しい画像を探す・作成する手間を省ける
- 実際のサイズは実行時に取得

### 判断3: Phase 1の機能範囲

**決定**: クリッピングのみ、アルファブレンディングは保留

**理由**:
- シンプルから始める（段階的な複雑性）
- 基本機能の検証が優先
- 必要性が明確になってから拡張
