# ADR-009: ゲームパッド入力（型・API 形・harness 整合）

**Status:** 承認（設計確定。backend 実装は follow-up タスク = TASK-80.2 以降）
**Date:** 2026-07-05
**Category:** プラットフォーム API・入力

## 概要

TASK-80 ファミリーで追加するゲームパッド（コントローラ）入力の設計を確定する。本タスク（80.1）は
backend 非依存の骨組み（型・facade スタブ・harness inject/probe・ヘルパー・example 雛形）のみを実装し、
実際の HID/IOKit/XInput 等の native 実装は 80.2 以降に委ねる。

**決定内容（要約）:**

1. **ポーリング主軸 + 接続イベント**: button/axis の連続値は `Window.getGamepadState(idx)` のポーリングで
   読む。接続/切断のみ `Event.gamepad_connected` / `Event.gamepad_disconnected` の一度きりイベントで通知する。
2. **標準レイアウト正規化**: 各 backend は native の raw レポートを、本 ADR で確定する固定レイアウト
   （`GamepadButton` 15 種 + 2 stick + 2 trigger）へ正規化して渡す契約とする。
3. **トリガー軸のみ**: L2/R2 はボタンとしては公開せず、`left_trigger`/`right_trigger`（f32 0..1）の
   analog 軸としてのみ表現する。
4. **deadzone は生値 + ヘルパー**: facade/harness は raw 値をそのまま返し、deadzone 適用は
   `src/gamepad.zig` の `applyDeadzone()` へ委ねる（opt-in）。
5. **harness state モデル**: harness が `gamepad_states: [MAX_GAMEPADS]?GamepadState` を保持し、
   `inject gamepad_connect/disconnect/button/axis` で更新する。`Window.getGamepadState` は facade の
   5 つ目のチョークポイントとして harness に interpose される。
6. **Event 末尾追加**: `Event` union の末尾に `gamepad_connected: GamepadInfo` /
   `gamepad_disconnected: GamepadDisconnect` を追加する（TASK-22 の `char_input` 追加と同じ
   「末尾追加 + 全 consumer 線形修正」パターン）。

## 背景

video-proto は keyboard（`KeyCode`/`KeyEvent`）・mouse（`MouseButton`/`MouseEvent`/`ScrollEvent`）を
`core/platform_types.zig` の共有型として持ち、`core/platform.zig`（facade）がイベント経路を、
`core/control/harness.zig` が入力注入・観測（probe）を提供している。ゲームパッドはこれらと異なり:

- ボタン数・軸数が多く（button 15 + stick 2 + trigger 2）、フレーム毎の連続値読み取りが主用途になる
  （キー入力のような「押した/離した」イベント通知だけでは冗長）。
- 接続/切断という非同期イベントが本質的に存在する（キーボード/マウスには無い概念）。
- macOS（IOKit/GameController.framework）・Linux（evdev/js API）・Windows（XInput/DirectInput）で
  raw レポートの形が大きく異なり、そのままでは backend 間で一貫した API になり得ない。

このため keyboard/mouse の「イベントのみ」モデルをそのまま踏襲せず、上記の設計判断を本 ADR で確定する。

## 用語

| 用語 | 定義 |
|---|---|
| **標準レイアウト** | 本 ADR が定義する backend 非依存のボタン/軸集合（下記「決定」節）。Xbox 系コントローラの配置を基準名にするが、実際の物理配置は backend の正規化ロジックに委ねる。 |
| **正規化** | 各 backend が native の raw レポート（HID usage / evdev code / XInput bitmask 等）を標準レイアウトへマッピングする処理（80.2 の責務）。 |
| **deadzone** | スティック中央付近の微小な入力揺れを無視する処理。本 ADR では facade/harness は適用せず、consumer 側が `applyDeadzone()` で opt-in 適用する。 |

## 決定

### 1. 標準レイアウト（AC#2 の型そのもの）

```zig
pub const MAX_GAMEPADS: u8 = 4;

pub const GamepadButton = enum(u8) {
    a, b, x, y,
    left_shoulder, right_shoulder,
    back, start,
    left_stick, right_stick, // スティック押し込み（クリック）
    dpad_up, dpad_down, dpad_left, dpad_right,
    guide, // Xbox ボタン相当（ホームボタン）
};

pub const GamepadButtons = packed struct(u32) {
    a: bool = false, b: bool = false, x: bool = false, y: bool = false,
    left_shoulder: bool = false, right_shoulder: bool = false,
    back: bool = false, start: bool = false,
    left_stick: bool = false, right_stick: bool = false,
    dpad_up: bool = false, dpad_down: bool = false,
    dpad_left: bool = false, dpad_right: bool = false,
    guide: bool = false,
    _reserved: u17 = 0,
    // isSet(btn) / set(btn, value) / toC() / fromC() を提供
};

pub const Stick = struct { x: f32 = 0, y: f32 = 0 }; // -1.0..1.0（raw、deadzone 未適用）

pub const GamepadState = struct {
    buttons: GamepadButtons = .{},
    left_stick: Stick = .{},
    right_stick: Stick = .{},
    left_trigger: f32 = 0,  // 0.0..1.0（raw）
    right_trigger: f32 = 0, // 0.0..1.0（raw）
};

pub const GAMEPAD_NAME_MAX: usize = 32;
pub const GamepadInfo = struct {
    index: u8,
    name_len: u8 = 0,
    name_buf: [GAMEPAD_NAME_MAX]u8 = [_]u8{0} ** GAMEPAD_NAME_MAX,
    pub fn name(self: *const GamepadInfo) []const u8 { return self.name_buf[0..self.name_len]; }
};

pub const GamepadDisconnect = struct { index: u8 };
```

**下位項目:**

1. **`GamepadButton` は exhaustive enum**（non-exhaustive `_,` を付けない）。固定 15 値の標準レイアウトで、
   拡張が必要になれば「末尾に値を追加」で足りる。non-exhaustive にすると `isSet`/`set`/`getButtonName`/
   harness parser の全箇所に「未知値」分岐を持たせる必要が生じ、コストが利点を上回るため見送った。
2. **トリガーはボタン集合に含めない**（AC#3）。物理的にボタンでもあるコントローラ（一部の廉価品）も、
   正規化時に axis へ統一する（80.2 の正規化ロジックの責務）。
3. **`GamepadInfo.name` のエンコーディング契約**: UTF-8 バイト列を最大 `GAMEPAD_NAME_MAX`(32) bytes まで
   コピーする。Zig 側は `name_len: u8` で使用長を管理し（NUL 終端は不要）、`name()` は
   `name_buf[0..name_len]` を返すだけ。C ABI 側（`platform.h` の `gamepad.name[33]`）は 32+NUL の
   固定長バッファとし、実装（80.2）は必ず NUL 終端し 32 bytes 超はその場で切り詰める。
4. **`MAX_GAMEPADS = 4`** は `core/platform_types.zig` を単一ソースとし、facade（`platform.MAX_GAMEPADS`）と
   harness（`gamepad_states` 配列長）の両方がそこから導出する（重複定義しない）。

### 2. API 形（AC#4）

```zig
// core/platform.zig（facade）
pub fn getGamepadState(self: Window, index: u8) ?GamepadState;
```

- **ポーリング関数は `Window` method**。既存 `lockFramebuffer`/`present` と同じ形状に揃える。
- **全 backend は当面 `null` を返すスタブ**（TASK-80.2 で各 backend が実装する）。**facade がスタブ自体を
  持つ**（`harness.isEnabled() or harness.isHeadlessActive()` なら harness へ委譲、そうでなければ無条件
  `null`）。backend ファイル（`platform_macos.zig`/`platform_linux*.zig`/`platform_windows*.zig`）は
  本タスクでは**無改造**（80.2 で `backend.Window.getGamepadState` が実装されたら facade がそこへ
  分岐するよう改める）。
- **接続/切断は `Event` 経由**。`Window.nextEvent()` が既存 4 backend の native 経路を持つ場合、
  80.2 の各 backend が `Event.gamepad_connected`/`gamepad_disconnected` を enqueue する（本タスクでは
  harness の `inject gamepad_connect/disconnect` のみが発火源）。

### 3. C ABI（AC#3。macOS backend 用。実消費は 80.2）

```c
typedef enum {
    PLATFORM_GAMEPAD_BUTTON_A = 0x0001,
    PLATFORM_GAMEPAD_BUTTON_B = 0x0002,
    PLATFORM_GAMEPAD_BUTTON_X = 0x0004,
    PLATFORM_GAMEPAD_BUTTON_Y = 0x0008,
    PLATFORM_GAMEPAD_BUTTON_LEFT_SHOULDER = 0x0010,
    PLATFORM_GAMEPAD_BUTTON_RIGHT_SHOULDER = 0x0020,
    PLATFORM_GAMEPAD_BUTTON_BACK = 0x0040,
    PLATFORM_GAMEPAD_BUTTON_START = 0x0080,
    PLATFORM_GAMEPAD_BUTTON_LEFT_STICK = 0x0100,
    PLATFORM_GAMEPAD_BUTTON_RIGHT_STICK = 0x0200,
    PLATFORM_GAMEPAD_BUTTON_DPAD_UP = 0x0400,
    PLATFORM_GAMEPAD_BUTTON_DPAD_DOWN = 0x0800,
    PLATFORM_GAMEPAD_BUTTON_DPAD_LEFT = 0x1000,
    PLATFORM_GAMEPAD_BUTTON_DPAD_RIGHT = 0x2000,
    PLATFORM_GAMEPAD_BUTTON_GUIDE = 0x4000,
} PlatformGamepadButtonFlags;

typedef struct PlatformGamepadState {
    uint32_t buttons_mask;
    float left_stick_x, left_stick_y;
    float right_stick_x, right_stick_y;
    float left_trigger, right_trigger;
} PlatformGamepadState;

#define PLATFORM_MAX_GAMEPADS 4

bool platform_get_gamepad_state(PlatformWindow* window, int index, PlatformGamepadState* out_state);
```

- ビット位置は Zig 側 `GamepadButtons` の宣言順と一致させる（`a=bit0` … `guide=bit14`）。
- `PlatformEventType` 末尾に `PLATFORM_EVENT_GAMEPAD_CONNECTED` / `PLATFORM_EVENT_GAMEPAD_DISCONNECTED` を
  追加し、`PlatformEvent.payload` に `gamepad{ int32_t index; char name[33]; }` を追加する（`name` は
  `PLATFORM_EVENT_GAMEPAD_DISCONNECTED` では空文字）。
- **本タスクは宣言のみ**。`platform_get_gamepad_state` を呼ぶコードは無いため、macOS の `.m`/`.swift`
  実装ファイルへの変更は不要（未使用 extern 宣言は link 要求を発生させない）。

### 4. harness への影響（AC#5）

1. **state 保持**: `gamepad_states: [MAX_GAMEPADS]?GamepadState` を module-level state として持つ
   （`inject_buf`/`mouse_buttons` 等と同じ「単一プロセスの debug facility」の設計に揃える）。
2. **inject コマンド**（既存の `key_down`/`mouse_down` 等と同じ文法系統に揃える）:
   ```text
   inject gamepad_connect <idx> [name]     # idx を接続状態にし GamepadState を既定値(全0)で生成
   inject gamepad_disconnect <idx>         # idx を未接続に戻す
   inject gamepad_button <idx> <button> <0|1>
   inject gamepad_axis <idx> <axis> <value>  # axis ∈ left_x/left_y/right_x/right_y/left_trigger/right_trigger
   ```
   - `gamepad_button`/`gamepad_axis` は**未接続 pad への操作を fail-fast で拒否**する（既存 inject の
     「不正トークンは注入されず state も汚さない」思想と同じ）。
   - `gamepad_axis` は**値域外を fail-fast で拒否**する（stick は `[-1,1]`、trigger は `[0,1]`）。
     raw 値契約（deadzone 未適用でもレンジは正規化済み）を守るため clamp ではなく reject を選ぶ。
3. **組み込み probe `gamepad`**（`fb`/`audio`/`stats`/`capabilities`/`capture` と同格の予約名）:
   ```text
   digest gamepad
   # connected=<bitmask> p0_buttons=<hex8> p0_lx=<d.4> p0_ly=<d.4> p0_rx=<d.4> p0_ry=<d.4> p0_lt=<d.4> p0_rt=<d.4> [p1_... ...]
   ```
   - 接続中の pad のみ列挙する（`connected` は全 pad の接続ビットマスク。`expect gamepad connected>0` 等で
     照合できる）。
   - key は top-level `k=v`（空白区切り）を保つため pad ごとに `p<idx>_` prefix を付ける
     （既存の `findKeyValue` の「top-level のみ抽出」規約に適合させるため）。
   - float は固定4桁 `{d:.4}` + 負ゼロ正規化（`v == 0` なら `+0.0` にしてから format）。表記ゆれによる
     `expect` の文字列不一致を防ぐ。
   - `buttons` は hex8（`{X:0>8}`）。既存 `crc={X:0>8}` と同じ幅。hex に文字（A-F）が入る値の `expect`
     比較は既存 crc と同じ「コピペ運用」（数値 parse できない場合は文字列完全一致にフォールバック）。
4. **`Window.getGamepadState` は facade の 5 つ目のチョークポイント**として harness に interpose する
   （既存4フック=`pollEvents`/`nextEvent`/`present`/`getTime` に次ぐ）。
5. **capabilities への反映**: `gamepad` を `CAPABILITY_BUILTINS` の末尾に追加する（既存の
   fb→audio→stats→capabilities→capture という追加順の延長）。

### 5. ヘルパー（AC#6）

`src/gamepad.zig`（`core/platform_types.zig` のみに依存。platform facade 不要 = headless で単体テスト可能）:

```zig
pub fn getButtonName(btn: GamepadButton) []const u8;
pub fn justPressed(prev: GamepadButtons, cur: GamepadButtons, button: GamepadButton) bool;
pub fn applyDeadzone(stick: Stick, dz: f32) Stick; // radial deadzone
```

`kit/kit.zig` に `pub const gamepad = @import("gamepad");` として再エクスポートする（`keyboard.zig` 等の
他の `src/` レガシーヘルパーは examples 専用で kit 非収録だが、`gamepad` は今後 apps からも直接使われうる
前提で kit に載せる）。

## 検証（既存契約に対する整合確認）

- **既存 caller 無改修**: `Event` union への末尾追加は既存 `else =>` を持つ switch には影響しない。
  `else` を持たない exhaustive switch（examples の `toGuiEvent` 系・`apps/patch`・`apps/editor/apps/pixie`
  の一部）には 1 行の no-op 分岐を追加する（TASK-22 の `char_input` 追加と同じ対応範囲）。
- **backend 実装可能性**: 全 backend が「facade 側で null を返すスタブ」を経由するため、本タスクでは
  backend 実装ファイルへの変更が一切不要（80.2 で個別に着手できる）。
- **harness 決定論との整合**: `gamepad_states` の更新は inject 処理時のみ（イベント時のみ = ホットパス
  ではない）。フレーム毎の `getGamepadState` 呼び出し自体は既存 state を読むだけで allocation/lock を
  伴わない。

## 影響

- `core/platform_types.zig`: `MAX_GAMEPADS`/`GamepadButton`/`GamepadButtons`/`Stick`/`GamepadState`/
  `GamepadInfo`/`GamepadDisconnect` の追加、`Event` union への2 variant 追加。
- `platform/platform.h`: C ABI 型・イベント種別・関数プロトタイプの後方互換な末尾追加（宣言のみ）。
- `core/platform.zig`: `Window.getGamepadState` スタブ + 型再エクスポート。
- `core/control/harness.zig`: `gamepad_states` state・inject 4種・組み込み probe `gamepad`。
- `src/gamepad.zig`: 新設ヘルパー（`kit/kit.zig` で再エクスポート）。
- `examples/22_gamepad`: 雛形 example（`run-example_22`。`examples/20_gamepad` という初期の想定番号は
  `20_capture_demo` が既に存在するため読み替え）。
- backend 実装ファイル（`platform_macos.zig`/`platform_linux*.zig`/`platform_windows*.zig`/macOS
  `.m`/`.swift`）は本タスクでは**無変更**（TASK-80.2 以降で着手）。

## ホットパス宣言

`Window.getGamepadState(idx)` はフレーム毎に呼ばれる想定（例: example は pad0..3 の4回/frame）。
4台×少数フィールドの固定長 copy（alloc/lock 無し）であり全画素ループでも RT（毎サンプル）でもないため、
`AGENT.md` の性能規約（SIMD 3点セット・cache_line 分離等）の適用対象外とする。harness の
`gamepad_states` 更新・`gamepad` probe の digest はイベント時のみ（inject/digest コマンド処理時に1回）
でホットパスではない。
