# ADR-007: プロジェクトの層構成と公開モジュール境界（core / libs / apps + kit）

**Status:** 承認
**Date:** 2026-07-04
**Category:** アーキテクチャ・ビルド構成・モジュール境界

## 概要

video-proto を「薄くて高速なマルチプラットフォーム基盤 ＋ それを使うアプリ群」として育てるにあたり、
`video-proto-main/` を **依存方向で厳密に層化**し、その境界を **build.zig のモジュールグラフで強制**する。
現状の `src/`（platform facade・各 backend・audio・harness・sprite/text/dsp が同居した“何でも箱”）を
解体し、新規に来るコード（TASK-62 の `framework/`、TASK-73 の `platform_wasm`、今後の serde/vg/timeline 等）が
最初から正しい場所に落ちる器を先に用意する。

**決定内容（規則として明文化）:**

- **R1 層と依存方向**: `apps → libs → core → platform` の一方向のみ許可する。逆流・層飛ばしの禁止。
  - **L0 `platform/`** — ネイティブ実装（C ABI + macOS objc/swift/metal 等）。現状のまま。
  - **L1 `core/`** — platform facade（`platform*.zig`）+ audio facade/backend（`audio*.zig`）+ `core/control/`。
    platform にのみ依存し、libs には依存しない**薄い base**。
  - **L2–L3 `libs/`** — 移植可能な再利用ライブラリ。**原則 platform に依存しない**（ヘッドレスで単体テスト可能）。
  - **L4 `apps/` / `examples/`** — 終端の消費者。
- **R2 libs は headless**: libs は platform の *実装* に依存しない（=`@import("platform")` しない）。
  入力イベント等の共有型が要る場合は、R6 の type-only モジュール経由でのみ参照する。
  現在 editor/core が既にこの規律なので、それを全 lib へ広げる。
- **R3 harness → `core/control` へ昇格**: `src/harness.zig` を `core/control/` へ移し、「テスト専用インフラ」から
  「制御＋観測プレーン（probe / action / drive / replay / 仮想クロック）」という**常設ランタイム機能**に格上げする。
  env 未設定で完全 no-op（通常実行の回帰ゼロ）の既定は維持する。
- **R4 `kit` 公開モジュール**: 安定サブセット（platform facade + core/control + 選抜 libs）を再エクスポートする
  umbrella モジュール `kit` を build.zig に定義する。**apps と外部消費者は個別ファイルではなく `@import("kit")` のみに依存**する。
  内部リファクタが消費者を壊さない境界をここで引く。
- **R5 apps は kit-only 消費者**: `apps/` 配下は kit しか import できない（build.zig で強制）。in-repo でも実質「外部消費者」扱いになり、
  境界が継続的に検証される。当面 apps は in-repo に残すが、卒業トリガ（R8）で兄弟 repo へ出せる。
- **R6 再利用 vs 終端で再分類**: 「app 配下か否か」ではなく「再利用可能か終端か」で置き場を決める。
  `apps/editor/core`（Canvas/Tool/Undo/PNG I/O。複数アプリで共有される再利用コア）は **libs へ格上げ**し、
  pixie/synth の**終端シェルだけ**を app として残す。共有型 `platform_types.zig` は type-only モジュールとして
  core から公開し、libs はそれのみ参照可（native 実装には依存させない）。
- **R7 heavy/optional は opt-in モジュール**: GPU compute・video decode・network 等の重い/任意能力は
  core に混ぜず、リンクしたアプリだけが重くなる独立モジュールにする。**core が太らないことが「薄さ」の実体**。
  既存の「audio backend は audio を使う exe にのみ link」を全 heavy lib へ適用。
- **R8 決定は今・移行は遅延**: 骨格（`core/` 新設・`kit` 定義・build.zig 依存強制・R6 の分類）は**今 1 回の意図的リファクタで作る**。
  既存ファイルの物理移動は**日和見**（次に触るとき正しい family へ移す）で進め、一括リライトはしない。
  app の repo 分割は「API が安定した／その app が独自リリース周期を持ちたくなった」時点で行う（それまでは in-repo が得）。

**目標レイアウト（family でグルーピング。lib 数が 8 を超えるため）:**

```
video-proto-main/
├── platform/            # L0 native（現状のまま）
├── core/                # L1 薄い base（platform に依存 / libs に依存しない）
│   ├── platform*.zig    #   facade + x11/wayland/gdi/d3d11/wasm backend
│   ├── audio*.zig       #   audio facade + backend
│   └── control/         #   ← harness 昇格（probe/action/drive/replay/仮想クロック）
├── libs/                # L2–L3 移植可能（原則 platform 非依存・単体テスト可）
│   ├── sys/   → serde / task / net …
│   ├── gfx/   → vg / color / png / font
│   ├── ui/    → gui
│   ├── audio/ → dsp（src/dsp から移動）/ synth
│   ├── time/  → timeline
│   └── paint/ → editor/core を格上げ（Canvas/Tool/Undo/PNG I/O）
├── apps/                # L4 kit-only 消費者: editor(pixie…) / synth
├── examples/            # 小さな単機能デモ（教材）
└── docs/  (adr/ plans/)
```

## 背景

- プロジェクトの旗を「**AI Agent フレンドリな薄くて高速なマルチプラットフォーム基盤 + それを利用したアプリ**」と定めた。
  この旗を**構造でも担保**したい：`libs` の headless 性（=AI が単体テスト・観測しやすい）、control plane の一級化、
  core の非肥大（=薄さ）を、規約でなくビルドで効かせる。
- 現状 `src/` は platform facade・各 backend・audio facade/backend・harness・sprite/text/dsp が同居しており、
  ここに新規コードを積み増すと確実に破綻する。実際、**TASK-62 の `framework/`（action/serialize/network 骨格）**と
  **TASK-73 の `platform_wasm`** が“今まさに”新ファイルの置き場を要求している。
- 再利用コードの置き場も不整合（`src/dsp` と `libs/synth`、`sprite`/`text` は `src/` だが `png`/`gui`/`font` は `libs/`）。
  今後 serde / vg / timeline / net / job といった土台 lib が控えており、器を決めないと散らばる。
- 外部利用は `tictactoe` が `.path` 依存で既に実証済み（公開境界の手本はある）。一方 in-repo の app は
  境界を無視して内部ファイルへ直接触れうるため、**境界の腐敗**が構造的リスクになっている。

## 比較検討

### 選択肢 A: 現状維持（`src/` フラット + apps in-repo で内部直参照）

- **メリット**: 追加コスト無し。今すぐ書ける。
- **デメリット**: 62/73 以降で `src/` が破綻。app が内部ファイルへ直参照し公開境界が腐る。
  「薄さ」「headless libs」を担保する仕組みが無い。→ **却下**。

### 選択肢 B: 今すぐ repo 分割（platform と apps を別 jj repo へ）

- **メリット**: 「これは基盤製品、apps は別物」という対外シグナルが最も強い。境界が物理的に強制される。
- **デメリット**: platform API がまだ激しく流動中（frame pacing TASK-34–38、control plane、serde/vg 未実装）。
  ここで分割すると**API を早すぎるタイミングで凍結**し、横断リネームが原子的でなくなる。
  かつ外側 `video-proto/` は既に兄弟 jj repo 群（main/backlog/tictactoe/zig-doc-builder）で、
  tictactoe が `.path` 消費を実証済み → **分割はいつでも安価にできる**ので、急いでやる利が無い。→ **却下（時期尚早）**。

### 選択肢 C: 層化 + build.zig 強制 + kit 境界（monorepo で境界を build graph で引く）【採用】

- **メリット**: in-repo の**原子的な横断リファクタ**（platform 変更と消費者修正を 1 コミットで land、`zig build test` で即検知）を保ちつつ、
  `kit`-only 消費で**公開境界を継続検証**でき、R7 で**薄さ**も守れる。「安価にいつでもできる分割（B）」を、必要になった時点（R8）に遅延実行できる。
- **デメリット**: build.zig のモジュールグラフ定義が複雑化する。`kit` に後方互換責任が生じる（バージョニングは本 ADR の範囲外・別途）。
- **判断**: 3 つの旗（薄い・高速・agent フレンドリ）と現在の API 流動性を踏まえると、C が唯一トレードオフを両立する。

### 補助的な論点：「再利用 vs 終端」の分類（R6）

「apps vs platform」で切ると `apps/editor/core` の扱いを誤る。これは複数アプリで共有される**再利用コア=lib**であって
app ではない。分類軸を「再利用可能か／終端か」に変えると、境界問題は**終端シェル（pixie/synth）だけ**に縮み、
判断が単純になる（R6・R8）。

## 影響（予測される結果）

- 新規コード（TASK-62 `framework/` → `core/control` 近傍、TASK-73 `platform_wasm` → `core/`）が
  **最初から正しい場所**に落ちる。器を先に作る効果が即座に出る。
- 既存ファイルの移動は**遅延**（R8）。big-bang リライトはしないので退行リスクを抑えられる。低リスクなもの
  （`src/dsp`→`libs/audio`、`sprite`/`text`→`libs/gfx`、`harness`→`core/control`、`editor/core`→`libs/paint`）から順次。
- build.zig にモジュールグラフと `kit` re-export を定義する。**依存方向違反がビルドエラー**になり、規約が機械的に守られる。
- **共有型の扱い**が実装上の要点になる：`platform_types`（KeyCode/Event 等）を type-only モジュールとして core から公開し、
  libs はそれのみ参照する（native impl に依存させない）。libs/gui がイベント型をどう受けるかは移行時に確定する（未決）。
- `kit` の**粒度**（どの lib を公開面に含めるか）は**成熟度で段階化し、狭く始める**方針とする（詳細な確定は外部出荷が近づいた時点で別 ADR）：
  - **初期 `kit` は安定済み lib のみ**＝`platform`(facade) / `control` / `types` / `audio` / `gui` / `png` / `font` / `dsp` / `synth`。
  - **流動中の lib（`serde` / `vg` / `timeline` / `net` 等）は `kit` に入れない**。app は当面これらを個別モジュールとして「内部・壊れうる」前提で直 import し、API が固まったら **`kit` へ昇格**する（成熟ゲート）。
  - `paint`（旧 `editor/core`）は汎用 `kit` ではなく「**エディタ族の共有 lib**」として扱い、pixie 等の該当 app だけが依存する。
  - この段階化は下記バージョニングと表裏：**`kit` に載る＝semver で守る対象**なので、semver を約束できないものは載せない。

### TASK-77 実装で確定した内容（2026-07-04）

- **未決 #1 の確定**: `platform_types` は **core が持つ type-only モジュール**として公開し（build.zig の
  `TaggedModule{ .layer=.core, .type_only=true }`）、libs は「core module のうち type-only なもの」だけを
  参照できる（`link()` の `.lib => dep.layer == .core and dep.type_only` 分岐で強制）。libs/gui は現状
  独自入力型を使うため今回の実装変更は無く、将来 gui がイベント型を共有する必要が出たら `platform_types`
  を直参照する（native impl・facade には依存させない）。
- **初期 `kit` セットに `audio`（core/audio facade）を追加**した（当初列挙から実装時に確定）。synth /
  modular / patch が L1 出力 facade を必須とし、facade は既に安定しているため。`types` も明示的に kit へ載せた。
- **R1 検査の実装**: build.zig に `Layer` enum（core=1/lib=2/kit=3/app=4）+ `TaggedModule` + `link()` を導入。
  逆流・層飛ばし・apps の非許可直 import は **build 構成時に `std.debug.panic`** で停止する。物理的にも各層は
  自ディレクトリに module root を持つため、配線されていない層への相対 `@import` は「file outside module path」で
  compile error になる（二重の防御）。
- **例外は 2 種のみ**（明示 API 経由で局所化）: ① `linkCoreException`＝ `harness(core/control) → png(libs/png)`
  の 1 箇所のみ（snapshot fb の PNG encode / crc32。png は依存ゼロの純 Zig 葉 lib で headless 性を壊さない）。
  ② `linkAppException`＝ app 内ファイルが pure-test root を兼ねる場合（`apps/modular/patch.zig` の synth/dsp）の
  named 直 import（kit と同一 module インスタンスで型同一性は保たれる）。
- **apps 直 import 許可リスト**（kit 非収録の流動 lib）: `modular` / `paint` / `viz`(spectrogram/scope)。
  `TaggedModule.app_direct_ok=true` で管理し、kit 収録 lib への app 直配線は panic で弾く。
- **examples は R5(kit-only) の対象外**とした（教材として従来の個別 module 配線を維持。`src/main.zig` も同扱い）。
- **物理移動の実施範囲**（低リスクのみ）: `src/platform*`・`src/audio*` → `core/`、`src/harness.zig` →
  `core/control/harness.zig`、`apps/editor/core/` → `libs/paint/src/`（root=paint.zig）、
  `apps/synth/{spectrogram,scope}.zig` → `libs/viz/src/`。**`src/dsp`・`sprite`・`text` 等は R8 で残置**
  （次に触るタスクで libs/audio・libs/gfx へ）。harness の module 名は churn 最小化のため `"harness"` のまま
  （`"control"` 改名は control/ が複数ファイル化する TASK-62.1/78 で判断）。
- `kit` の**バージョニング/semver** は本 ADR では未確定。実際に外部出荷が近づいた時点で別 ADR で決める。
- examples 単体ビルドの `build_helpers` symlink workaround（AGENT.md 記載の Windows 制約含む）は本 ADR の対象外。
  `kit` 化で将来解消の道筋はできるが、ここでは触らない。
- app の repo 分割（R8 卒業）は、`kit` にしか依存していないため**非イベント**として実施できる。
