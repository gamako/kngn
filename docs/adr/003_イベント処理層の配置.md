# ADR-003: イベント処理層の配置 - Platform層での実装

**Status:** 承認
**Date:** 2025-10-25
**Category:** アーキテクチャ・API設計

## 概要

イベント処理システムにおいて、ネイティブイベント（NSEvent、MSG等）から統一イベント構造体（PlatformEvent）への変換をどの層で行うかを決定した。

**決定内容：**
各プラットフォーム実装（Objective-C/Swift/Metal）内でネイティブイベントをPlatformEvent構造体に変換し、統一されたC APIとして提供する。

## 背景

02_keyboard_inputサンプルの実装にあたり、イベント処理システムの設計が必要になった。主な検討事項：

1. **現状の課題**
   - `platform_poll_events()`は実装済みだが、イベント取得のみ
   - `platform_get_event()`およびPlatformEvent型が未定義
   - イベント処理層の配置が設計上の重要な判断点

2. **アーキテクチャの選択肢**
   - イベント変換をPlatform層で行うか
   - Zig層で共通処理として実装するか

## 比較検討

### Architecture A: Platform側で変換（採用）

```
macOS NSEvent ─┐
               ├→ [Platform層(C/Swift)] → PlatformEvent → [Zig層]
Windows MSG ───┘   ・変換ロジック
                   ・キュー管理
                   ・統一構造体
```

**メリット：**
- FFI境界がシンプル（統一構造体でやり取り）
- デバッグが容易（プラットフォーム側で完結）
- プラットフォーム固有の最適化が可能
- 型安全性が高い（C構造体で明確）

**デメリット：**
- 各プラットフォームで変換ロジックの重複（約540行程度）
- テストをプラットフォームごとに必要

### Architecture B: Zig側で変換（却下）

```
macOS NSEvent ─┐
               ├→ [Platform層(薄い)] → RawEvent → [Zig共通層] → PlatformEvent
Windows MSG ───┘   ・最小限のFFI        ・変換ロジック(共通)
                                        ・キュー管理(共通)
```

**メリット：**
- コード共通化（キュー管理、キーコード変換など）
- Zigでの統一テストが可能
- 拡張時の修正箇所が少ない

**デメリット：**
- FFI境界が複雑（生データの受け渡し）
- デバッグが困難（両側のコードを確認必要）
- 汎用パラメータによる型安全性の低下
- パフォーマンスへの影響（変換が2回発生する可能性）

## 決定理由

**Architecture A（Platform側変換）を採用した理由：**

1. **FFI境界のシンプル化**
   - 明確に定義された構造体でやり取りするため、デバッグが格段に容易
   - エラーの原因特定が簡単

2. **将来の複雑な機能への対応**
   - IME（Input Method Editor）などの高度な機能はOS固有APIとの密結合が必要
   - 結局Platform層が厚くなることが予想される
   - 「完璧な抽象化」を求めすぎると、かえって複雑になる

3. **限定的なプラットフォーム数**
   - 現在はmacOS、将来的にWindowsとLinux/Waylandのみ
   - 540行程度の重複は許容範囲内

4. **プロジェクト原則との整合性**
   - PLAN.mdの「シンプルさ優先」原則に合致
   - Unix哲学に従い、各層の責任を明確に分離

## 実装方針

### 責任の分離

**Platform層の責任：**
- ネイティブイベントの取得
- 仮想キーコードへの変換
- イベントキューの管理（リングバッファ）
- モディファイアキーの状態管理

**Zig層の責任：**
- イベントの解釈とアプリケーションロジック
- 複数キーの組み合わせ判定
- アプリケーション固有の処理

### 将来の移行パス

もし将来的に以下の状況になった場合、再検討する：
- プラットフォームが5個以上に増えた
- イベント処理がもっと複雑になった（ジェスチャー、高度なIMEなど）
- 共通バグが頻発した

その際は、既存APIを壊さずに共通層を追加できる設計としている。

## 影響

- `platform.h`にPlatformEvent構造体とplatform_get_event()関数を追加
- 各プラットフォーム実装にイベントキューとネイティブイベント変換ロジックを実装
- Zig層はシンプルなイベント処理ループを実装するだけでよい
